# 校园网实测结论与经验教训

> 整理时间：2026-09-19
> 来源：路由器版（OpenWrt）双线上行改造过程中的实测。所有数字都是在本校校园网、路由器（小米 AX3000T / Kwrt 24.10）和一台 Windows 电脑上量出来的。
>
> 这份文档同时是**桌面端脚本更新前的依据**，第四节直接给出了改动清单。

## 一、校园网本身的规律

### 1.1 限速是按「账号」的，不是按「路径」

这是本次最重要的结论，也推翻了我最初"有线网段慢"的错误判断。

| 账号 | 走有线 | 走无线（2.4G/5G） |
| --- | --- | --- |
| 学生账号 | **65~83 Mbps** | **63~79 Mbps** |
| 教师账号 | **17~21 Mbps** | **17~21 Mbps** |

同一条线、同一台设备，**只换账号，速度差 3~4 倍**；同一个账号换路径，速度基本不变。

**对脚本的含义**：不要试图通过换网段、换路径来提速，那没用。要提速只能换账号。

### 1.2 每个账号的并发会话上限是 2 条

超出时报：

```
Msg=01;msga='运营商账号在线数超出限制，请联系运营商处理(Rad:Limit Users Err)'
```

实测：同一个账号同时开 2 条会话是允许的（各得 17~18 Mbps），第 3 条被拒。

**对脚本的含义**：

- 多设备/多线路共用账号时要算清楚占用了几条
- 路由器占 1 条 + 电脑占 1 条 = 刚好用满，手机就不能再单独认证了

### 1.3 认证是绑定「终端 IP」的

- 服务端记录的是**终端 IP 的认证状态**，不是设备
- 同一个 IP 上不能再登录第二个账号，会返回 `终端IP已在线！`
- 想换账号，**必须先让那个 IP 上的会话失效**（或换一个 IP）

会话残留时间实测约 **2.5 小时**（断开连接后仍会在服务端占着）。

**对脚本的含义**：改账号后不会立刻生效；如果那条线的 IP 已经被认证过，脚本会认为"已在线"而跳过登录。测试换账号时要预留时间或换 IP。

### 1.4 服务类型后缀只对绑定了运营商的账号有效

Dr.COM 表单支持给账号加后缀选择服务类型：无后缀（校园用户）/ `@njxy` / `@dx`（电信）/ `@lt`（联通）。

| 服务类型 | 教师账号的结果 |
| --- | --- |
| 无后缀（默认） | `Login succeed`，17~21 Mbps |
| `@njxy` | `Login succeed`，**16.6 Mbps（无区别）** |
| `@dx` | `Authentication fail` |
| `@lt` | `Authentication fail` |

**对脚本的含义**：

- `Authentication fail` 说明这个服务类型对该账号无效，应继续试下一个（现有逻辑已正确处理）
- **不要指望换服务类型能提速**——实测无差别
- 没配 `wifi_suffix` 时脚本会依次尝试多个后缀，对没绑运营商的账号会白打几次请求；知道自己属于哪种就把它填上

### 1.5 网段划分

| 网段 | 类型 | 门户行为 |
| --- | --- | --- |
| `10.12.x.x` | 有线 | 走统一身份认证（或 Dr.COM 表单） |
| `10.54.x.x` | 无线 | 走 Dr.COM 门户表单（`DDDDD`/`upass`） |

这一段和 `campus_http.py` 里的 `CAS_RANGES` / `needs_cas()` 判断一致，实测无误。

### 1.6 关于夜间断网

文档里默认按"学生账号周一~周五 00:00-06:00 被断"来设计（`quiet_hours`）。
实测某晚 **03:33 学生账号仍在线**，即学校当晚并没有执行零点断网。**策略存在但执行不稳定**，所以脚本的夜间静默仍然要保留（被断时不去撞墙），但不要假设它一定生效。

## 二、写脚本会踩的坑

### 2.1 `http.client` 的 `_create_connection` 是**实例属性**

```python
class HTTPConnection:
    def __init__(self, ...):
        self._create_connection = socket.create_connection   # ← 实例属性，会盖住子类方法
```

所以在子类里覆写 `_create_connection` **完全无效**，必须在 `super().__init__()` 之后重新赋值：

```python
class MyConn(http.client.HTTPConnection):
    def __init__(self, *a, device=None, **kw):
        super().__init__(*a, **kw)
        self._create_connection = lambda addr, timeout=None, source_address=None: \
            my_create_socket(addr, timeout, source_address, device)
```

这个坑让"绑网卡"静默失效过一次——包照样从默认路由出去，看不出报错。

### 2.2 判断"在线"不能只认 HTTP 200

`http://www.baidu.com/` 在校园网里返回的是 **302 跳转 HTTPS**。绑定出口时用的是底层 `http.client`，**它不自动跟随跳转**，所以只认 200 会把"其实已经通了"判成失败。

正确做法：**2xx 和 3xx 都算通**，但页面或跳转地址里出现门户标记（`Dr.COMWebLogin` / `DrcomServer` / `eportal` / `10.255.255.2`）就一律算没通。

### 2.3 Linux 不看源地址选路，Windows 看

这是跨平台最反直觉的一点：

| 平台 | `bind(源地址)` 能否改变走哪张网卡 |
| --- | --- |
| **Windows** | ✅ 能。路由决策会参考绑定的源地址 |
| **Linux** | ❌ 不能。路由只看**目的地址**，包会顺着默认路由出去（再被 SNAT 改成出口地址） |

在 Linux 上要让「某个源地址的包走某张网卡」，必须加**策略路由**：

```sh
ip route replace default via <网关> dev <网卡> table <表号>
ip rule add from <源地址> lookup <表号> priority 500
```

优先级要排在 mwan3 的 `fwmark` 规则（1001+）之前。

### 2.4 `SO_BINDTODEVICE` 在无线网卡上不生效

在 MT7981 + OpenWrt 24.10 上实测：

```
绑定 wan        -> 源地址 10.12.36.7          ✅
绑定 phy0-sta0  -> 失败 OSError: Host is unreachable   ❌
```

**结论：优先"把网卡名解析成当前 IPv4，按源地址绑定"，`SO_BINDTODEVICE` 只作为拿不到地址时的兜底。** 而且 DHCP 续约后地址会变，解析结果要设缓存（60 秒左右重解析一次）。

### 2.5 别忘了 `import subprocess`

路由器版脚本里 `device_ipv4()` 用 `subprocess.run(["ip", ...])` 拿地址，但漏了 `import subprocess`。异常被 `except Exception` 吞掉，表现是"悄无声息地返回 None"，排查了很久。

**教训**：捕获范围过宽的 `except` 一定要配日志，否则会掩盖真 bug。

### 2.6 内存：一个脚本进程约 24 MB

实测 `VmRSS ≈ 24 MB`。在只剩 20 MB 可用的路由器上：

- ❌ 起两个进程（2 × 24 MB）装不下
- ✅ 一个进程里跑多条线路（多一个 Session 对象，约 +3~4 MB）

多线路用 `contextvars` 让每个线程看到自己的目录/日志，配合"路径代理"可以让全文 30 多处用法一行都不用改。

## 三、路由器侧：mwan3 多线路

### 3.1 接口必须加入 WAN 防火墙 zone，否则没有 NAT

这是最隐蔽的一个坑：接口起来了、路由表也建了、mwan3 分流标记也正常，但**那条线的流量永远是 0**。

原因：防火墙的 wan zone 里只有 `wan`，新接口不在其中 → **不执行 masquerade** → 转发的包带着内网源地址 `192.168.5.x` 出去 → 被校园网直接丢掉。

```sh
uci add_list firewall.@zone[1].network='wanb'
uci commit firewall && /etc/init.d/firewall reload
```

> 排查时容易误判成 mwan3 的 sticky 问题——因为现象都是"标记正常但没有流量"。**先查 masquerade。**

### 3.2 `https` 规则默认 `sticky=1` 会把客户端粘死在一条线上

`config rule 'https'` 默认 `sticky '1'`，效果是**同一个源地址的所有 HTTPS 连接固定在一条线**上。做负载均衡时要改成 `sticky '0'`。

### 3.3 默认检测参数过于保守：切换要 110 秒

mwan3track 的默认值：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `interval` | 10 秒 | 检查间隔 |
| `timeout` | 4 秒 | 单次 ping 超时 |
| `down` | 5 次 | 连续失败几次判定掉线 |
| `up` | 5 次 | 连续成功几次判定恢复 |

**实测：从断线到完全切到备用线用了 110 秒。** 这期间流量还在往死线上走，表现为"网卡住但没断"。

调成 `interval=3 / timeout=2 / down=2 / up=2` 后，**实测 21 秒**。

### 3.4 mwan3 规则按配置文件顺序匹配

源地址规则必须排在 `https`（匹配 443 端口）和 `default_rule` 之前，否则会被它们先接走：

```sh
uci set mwan3.pc_wanb=rule
uci set mwan3.pc_wanb.src_ip='192.168.5.209'
uci set mwan3.pc_wanb.use_policy='wanb_only'
uci reorder mwan3.pc_wanb=0        # ← 关键，放到最前面
```

### 3.5 两条线"负载均衡"的带宽增益很小

实测（8 连接、同站点、20 秒）：

| 配置 | 合计 |
| --- | --- |
| 只走快线 | 75.5 Mbps |
| 两条线负载均衡 | **78.3 Mbps** |

**只有 4% 增益。** 原因是两条线都从同一台宿舍 AP 出去，共用那段上行；而慢线本身只有 18 Mbps，分 20% 的连接过去反而会拖慢。

**结论：这种情况更适合「主备」——快线为主、慢线待命。** 平时全部走快线（满速、无干扰），快线挂了才切过去。

### 3.6 一次只改一个变量

有一次同时做了「关掉硬件流量加速」+「启用 mwan3 的第二条线」+「重启 mwan3」，路由器随后两次意外重启（间隔约 10 分钟）。

后来拆开单独验证：

- 只关流量加速 → 稳定 30 分钟 ✅
- 只启用 mwan3 第二条线（加速已关）→ 稳定 22 小时 ✅

**教训**：网络设备上改动要一步一验证，尤其是加速/卸载这类会动硬件状态的开关。

## 四、桌面端脚本改动清单

面向 `campus_http.py`（纯 HTTP 版）。已具备的不再列出。

### 4.1 高优先级

| # | 改动 | 原因 |
| --- | --- | --- |
| 1 | **加 `account_type`（student / teacher）+ `--mode` 命令** | 学生账号夜间会被断，脚本要按类型决定是否静默；教师账号则整夜跑。路由器端已实现，桌面端对齐即可 |
| 2 | **教师模式关闭失败退避**（仅保留"账号级问题"冷启动） | 教师账号 24 小时在线，网络一恢复就该立刻登录，不该干等 2/5/15/30 分钟 |
| 3 | **`--bind` 的说明写进 README**（已实现但没文档化） | 同时插网线和连 WiFi 时，浏览器登录页会走有线显示"已登录"；必须用 `--bind wifi` 让认证走无线 |
| 4 | **会话数自检提醒** | 每个账号只有 2 条会话；脚本重启、频繁重连会占用槽位。可在日志里提示当前是第几条 |

### 4.2 中优先级

| # | 改动 | 原因 |
| --- | --- | --- |
| 5 | `--bind` 支持传**网卡名**（自动解析成 IP） | 目前只接受 IP，用户不容易查到自己的无线地址。Windows 下解析成 IP 后绑定即可（Windows 会看源地址选路，不需要策略路由） |
| 6 | 换账号后**主动提示会话残留** | "改完账号不会立刻生效，旧会话最长要 2.5 小时才释放" |
| 7 | 日志里记录**当前账号的实测速率参考值** | 学生 ~65，教师 ~18，方便一眼看出是不是被限速了 |

### 4.3 明确**不要**做的事

| 不做 | 原因 |
| --- | --- |
| ❌ 在桌面端做"按服务类型后缀提速" | 实测无差别 |
| ❌ 用改接口跃点的方式"负载均衡" | Windows 没有多链路聚合；改跃点只是选一条用 |
| ❌ 在桌面端实现策略路由 | 那是 Linux 才需要的；Windows 绑源地址就够了 |

### 4.4 桌面端做多链路叠加的可行性

**Windows 原生做不到。** NIC Teaming 只支持服务器版且要求同一网段；改跃点只是选一条用。

| 方法 | 能否叠加 |
| --- | --- |
| Windows 原生 | ❌ |
| 改接口跃点 | ❌（只是选路） |
| ForceBindIP | ⚠️ 把**某个程序**绑到某张网卡，属于分流不是叠加 |
| Speedify 等付费 VPN | ✅ 真叠加，但要订阅 + 多一层延迟 |

**注意区分两种情形**：

- 电脑的网线和 WiFi 都连**同一台路由器** → 做不做都一样，瓶颈在路由器上游
- 电脑的 WiFi 直连**校园网**、网线走路由器 → 这时才是两条独立出口，叠加才有意义

## 六、最终采用的路由器配置

```
wan  (有线)   学生账号  —— 主用，65~83 Mbps
wanb (2.4G)   教师账号  —— 待命，18 Mbps（24 小时可用）

策略：主备（wan_wanb）—— 平时全走学生线，挂了 21 秒切到教师线
额外规则：192.168.5.209（某台设备）固定走教师线，永不参与切换
```

配置思路同样适用于桌面端：**快账号当主力，24 小时可用的账号当兜底。**
