# 技术细节

这份文档记录认证流程的逆向结果、踩过的坑和调试方法，供后续维护参考。
所有结论都在 2026-09-15 于南艺校园网实测得到。

---

## 一、认证链路

学校有两套认证界面，门户（Dr.COM ePortal v4.0，`10.255.255.2`）根据**客户端 IP** 决定用哪套。
判断规则就写在门户页面的 JS 里：

```javascript
if ((ip >= '1.1.1.1' && ip <= '10.51.255.255') ||
    (ip >= '10.128.0.1' && ip <= '10.129.255.255')) {
    window.location = 'https://c.nua.edu.cn/cas/wifiLogin/innerLogin.jsp';
}
```

脚本里 `needs_cas()` 复刻了同一套判断，并直接解析门户页面中它自己写出的客户端地址（`v46ip`），
保证和浏览器看到的一致。

### 默认：Dr.COM 门户表单（有线 / 无线通用）

2026-09-16 实测确认：**Dr.COM 的登录接口并不拒绝有线客户端**。门户只是用 JS 把有线用户
「引导」到统一认证页，但直接调用 Dr.COM 的接口同样有效，而且能绕开统一认证必须完成的
验证环节（拼图滑块 / 人脸识别），也不需要 RSA 加密。

```
POST http://10.255.255.2:801/eportal/?c=ACSetting&a=Login&ver=1.0
     X-Requested-With: XMLHttpRequest
     Host: 10.255.255.2              （不带端口）
     DDDDD=<账号>&upass=<密码>&0MKKey=123456&R6=0&terminal_type=1&lang=zh-cn&url=drappall
     → 成功: <!--Dr.COMWebLoginID_3.htm--> Login succeed.
```

有线网段上的验证（用假账号探测，本机当时已在线）：

- `/eportal/?c=ACSetting&a=Login&ver=1.0`（POST）→ `msga='终端IP已在线！'`
- `/eportal/portal/login?callback=dr1003&login_method=1&user_account=,0,<账号>&user_password=…`（GET）
  → `{"result":0,"msg":"终端IP已在线！","ret_code":2}`

两个接口都**按登录请求处理**（回的是"已在线"而不是"账号错误"），说明有线确实能走这条路。
注意新版接口的账号字段是 `user_account=,0,<账号>` 这种带前缀的写法，用 `DDDDD` 会得到
「无法获取用户认证账号」。

**端到端实测（2026-09-16 16:34）**：禁用有线网卡 5 分钟让 AC 清掉会话，恢复后在
「在校园网且未认证」状态下自动登录——

```
有线网段（客户端 10.12.x.x）→ 优先走 Dr.COM 表单（可绕开统一认证的验证环节）
Dr.COM 登录：接口 ACSetting，服务类型 校园用户(默认)
  → <!--Dr.COMWebLoginID_3.htm--> Login succeed.
登录成功，网络已恢复           （从开始到恢复 1 秒）
```

即有线链路**完全不再依赖统一身份认证**，也就不会遇到滑块或人脸识别。

对应配置：`config.json` 的 `wired_flow`（默认 `drcom`；改成 `cas` 可强制走统一认证。
两种方式都会在失败时自动试另一种，除非遇到需要人工处理的错误）。

### 后备：统一身份认证（CAS）

```
GET  http://10.255.255.2/                      门户页面（JS 跳转）
GET  https://c.nua.edu.cn/cas/login?service=…  认证页（#username / #passwordShow）
POST /cas/login?service=…                      提交账号密码
     → 服务器返回「请完成安全验证」页（滑块这时才出现）
POST /cas/captchValid/checkCaptchImg           上报"验证通过"
POST /cas/login?service=…（空表单 fm4）         登录完成
```

> ⚠️ **部分账号的安全验证是人脸识别而不是拼图滑块**：页面上两套 DOM 同时存在
> （`slidingbox` + `canvas#canvas` / `faceData` / `loginType=4`），光看 HTML 容易误判。
> 人脸识别需要真人对着摄像头，自动化无法完成——这类账号请用默认的 Dr.COM 表单那条路。

要点：

1. **滑块是提交之后才出现的**。登录页里 `.slidingverification` 默认带 `none` 类（隐藏），
   点了「登录」服务器返回的页面才把它显示出来。**先解滑块再提交是无效的。**
2. 滑块判定完全是前端的：`Math.abs(tip.offsetLeft - shadow.offsetLeft) <= 2`。
   验证页的 `loginCaptch.js` 在拖拽成功后会：
   ```javascript
   $.ajax({ url: contextPath + "/captchValid/checkCaptchImg",
            data: { request_username, captchResult: "1" },
            success: () => document.getElementById("fm4").submit() });
   ```
3. **`contextPath` 是 `/cas`**，所以上报地址是 `/cas/captchValid/checkCaptchImg`。
   写成 `/captchValid/...` 会得到 **404**，而且后面所有提交都不会生效。
   脚本现在会从验证页里动态解析 `contextPath`，不再写死。

### 校园无线：Dr.COM 门户表单

```
GET  http://10.255.255.2/                            门户页面（显示自己的登录表单）
POST http://10.255.255.2:801/eportal/?c=ACSetting&a=Login&ver=1.0
     字段: DDDDD=<账号> upass=<密码> 0MKKey=123456 url=drappall …
     → 成功时返回 <!--Dr.COMWebLoginID_3.htm--> Login succeed.
```

三个必须一致的细节（错一个就会拿到后台管理页面而不是登录结果）：

| 细节 | 说明 |
| --- | --- |
| URL 带 `ver=1.0` | 门户配置里给的 `authloginpath` 不带 ver，必须自己补 |
| 带 `X-Requested-With: XMLHttpRequest` | 否则 AC 判定为普通页面请求 |
| `Host` 头不带端口 | `Host: 10.255.255.2`，不是 `10.255.255.2:801` |

另外，新版接口 `/eportal/portal/login` 在本校**始终返回**「无法获取用户认证账号」，
脚本只在旧接口也认不出账号时才去试它。

「服务类型」对应门户的运营商选项：默认「校园用户」（账号不带后缀），
另有「校园电信 `@dx`」「校园联通 `@lt`」。脚本按此顺序尝试，
也可以在 `config.json` 里用 `wifi_suffix` 固定其中一种。

## 二、密码加密（学校页面同款，非标准 PKCS#1）

认证页的 `security.js` 用的是「教科书式 RSA + 零填充 + 小端字节序」：

```javascript
RSAUtils.encryptedString = function (key, s) {
    var a = [];  // 每个字符取 charCodeAt，按字节放进数组
    while (a.length % key.chunkSize != 0) a[i++] = 0;   // 尾部补 0 到整块
    for (each chunk) {
        block.digits[j] = a[k] + (a[k+1] << 8);         // 小端 16 位字
        crypt = barrett.powMod(block, key.e);           // 直接模幂，无填充
    }
};
```

也就是说 `m = little_endian(明文 + 补零)`，`c = pow(m, 65537, n)`，输出十六进制。
**用标准 RSA 库（PKCS#1 填充）会得到完全不同的结果，服务器解不出来。**

`campus_http.rsa_encrypt()` 用 Python 标准库复刻了这套算法，
并用 `tools/selftest_rsa.py` 与学校页面自己的函数**逐字节比对**（6/6 通过，
覆盖单块 / 满块 / 跨块长密码）。

## 三、判断"当前是否已认证"

不能只看学校的状态接口：

- 有线会话查 `https://c.nua.edu.cn/cas/wifiLogin/isLogin`
- 无线会话走的是 Dr.COM，该接口可能返回"未登录"

所以 `is_online()` 会：先查接口，如果接口说未登录（或接口不可用），
再**真实访问一次外网**复核——未认证时请求会被门户劫持，一眼就能看出来。

另外门户把 `www.msftncsi.com`、`captive.apple.com`、`generate_204` 等
放进了访问黑名单，**不能用这些地址做连通性判断**。

## 四、夜间限制与失败退避

- `quiet_hours`：默认周一~周五 00:00–06:00 完全不尝试（判断在网络操作之前，
  连请求都不发），只在进入/离开时各记一行日志。
- `failure_backoff`：登录失败后按 2/5/15/30 分钟放慢重试，成功即恢复。

两者都只在"模式变化"时写日志，所以日志文件平时非常干净。

## 五、调试方法

### 不影响正常连接地调试无线流程

电脑同时连着有线和无线时，把请求**绑定到无线网卡的源地址**发出，
门户就会按无线客户端来响应——不用拔网线：

```bash
python tools/probe_wifi.py                 # 看无线走哪套流程
python tools/probe_drcom.py                # 用假账号试各种登录参数格式
```

### 安全地试参数

`tools/probe_drcom.py` 使用**不存在的假账号**探测接口，
不会影响真实账号，也不会真的登录成功。

### 强制重新认证（复现断网）

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\restart_nic.ps1 -Seconds 300
```

实测：禁用有线网卡 **2 分钟不足以**让 AC 清掉会话，**5 分钟可以**。
脚本禁用网卡时会同时拉起一个独立的兜底进程，即使窗口被关掉也会到点恢复网卡。

### 自测

```bash
python tools/selftest_rsa.py      # 加密实现 vs 学校页面实现（需联网打开认证页）
python tools/selftest_forms.py    # 两种登录页的表单识别与填写
python tools/selftest_slider.py   # 滑块拖拽逻辑（本地复刻页，不碰学校系统）
```

## 六、已知情况

- **安全验证可能是人脸识别**：有线走 CAS 时，部分账号的「安全验证」是人脸识别（`loginType=4`），
  自动化做不到。默认走 Dr.COM 表单可以绕开。
- **账号有并发在线数限制**（实测上限 2 个会话）。错误原文：
  `msga='运营商账号在线数超出限制，请联系运营商处理(Rad:Limit Users Err)'`。
  这不是密码错误。而且会话按 MAC/IP 记在 RADIUS 上，客户端离开后**旧会话会残留 7~10 分钟**
  才释放，这期间新设备登录会被拒。脚本已经把这类提示当作"致命错误"立即停手，
  并把 AC 的原话写进日志（避免用户以为密码错了反复试而把账号撞锁）。
- **学校可能有两套密码**：校园无线（Dr.COM）用「上网密码」，有线（统一认证）用
  「统一身份认证密码」，实测两者可能不同（甚至只差一个字符）。CAS 那条还有失败计数，
  反复试错可能锁定账号。目前实现只存一套密码；如果两个流程一个成功一个报"密码错误"，
  就是这个原因。
- **服务类型（运营商）按 Wi-Fi 不同**：`NUA-CMCC`（移动）用不带后缀的学号；
  `NUA-@f-Young`（电信）用 `学号@dx`。用错后缀时会返回
  `账号错误(运营商登录请先绑定运营商账号)` 或 `Authentication fail`——**这类错误不算致命**，
  应该继续试下一个后缀；脚本会依次尝试 无后缀 → `@njxy` → `@dx` → `@lt`。
- **注销接口故障**：`/cas/wifiLogin/isLogout` 返回 `{"msg":"Radius注销失败！"}`，
  Dr.COM 门户注销返回 `Logout failed.`。这是学校服务端问题，用户无法主动下线。
- **校园无线依赖运营商出口**：无线那段按"服务类型"走，默认「校园用户」实测可用。
- **无线若要求图形验证码**：纯 HTTP 模式无法识别（那是图片识别，不是位置比对），
  此时应改用浏览器模式。
