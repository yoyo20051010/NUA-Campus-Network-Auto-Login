# 实测反馈：几个会影响 Windows 版的坑（2026-09-15 ~ 16）

做 macOS 适配时把整套流程在真实环境跑了一遍（有线 + 无线 + 全局 VPN + 半夜断网），
下面几条对原版 Windows 版同样适用，按重要性排序。

---

## 1️⃣ 有线网段的"安全验证"是人脸识别，不是拼图滑块 ⚠️

原版文档写的是"提交之后返回拼图滑块页"，但实测（南艺，2026-09）提交账号密码后
服务器返回的安全验证页是**人脸识别**：

```html
<h1>人脸识别失败，请选择后继续操作</h1>
<canvas id="canvas" width="412" height="412"></canvas>
<input name="faceData" value=""/>
<input name="loginType" value="4"/>       <!-- 4 = 人脸识别 -->
请保证光线适中，正视摄像头 … 正在启用人脸识别…
```

页面里确实**同时存在** `slidingbox` 那套 DOM（所以看 HTML 会以为有滑块），
但真正生效的验证是刷脸 —— 机器自动化不了（没有真人对着摄像头，必然"人脸识别失败"）。

**影响**：原版"有线走统一认证"这条路在有摄像头之外的场景**无法自动完成**。

**建议**：见第 2 条 —— 换一条路。

---

## 2️⃣ Dr.COM 表单在有线网段也能用（可以绕开人脸识别）✅

学校是用门户里的 JS **把有线客户端"引导"**到统一认证页的（按客户端 IP 判断），
但 Dr.COM 自己的登录接口并不拒绝有线 IP。实测在有线网段（10.12.x）直接提交：

```
POST http://10.255.255.2:801/eportal/?c=ACSetting&a=Login&ver=1.0
X-Requested-With: XMLHttpRequest
DDDDD=<账号>&upass=<上网密码>&0MKKey=123456&R6=0&terminal_type=1&lang=zh-cn&url=drappall
```

返回：

```html
<!--Dr.COMWebLoginID_3.htm--> <body> Login succeed. </body>
```

之后有线立即恢复上网（探针 401→204）。

**建议**：把"有线必走统一认证"改成可配置，默认两段都走 Dr.COM 表单。
好处：① 绕开人脸识别；② 两套流程合并成一套，代码更简单；③ 不需要 RSA 和滑块逻辑。

> 我们这边把 `wired_flow` 做成配置项（默认 `drcom`，可改回 `cas`）。

## 3️⃣ 账号有"并发在线设备数"限制

登录时可能返回：

```
msga='运营商账号在线数超出限制，请联系运营商处理(Rad:Limit Users Err)'
```

**这不是密码错误**，而是该账号的同时在线会话数满了（实测上限 2）。

坑在于：会话是**按 MAC/IP 记在 RADIUS 上的**，客户端走了（拔网线、换 MAC、关 WiFi）
之后**旧会话还会挂 7~10 分钟**才释放。这期间新设备登录会被拒。

我们还遇到一种情况：关掉 WiFi 8 分钟，回来仍然"已在线"（会话没释放）。

**建议**：识别这个错误码后**立即停止重试**（换服务类型/换接口都没用），
并把原话写进日志，避免用户以为是自己密码错了而反复试。

## 4️⃣ 学校有两套密码（可能只差一个字符）

| 用途 | 走哪套 | 密码 |
| --- | --- | --- |
| 校园无线（Dr.COM 门户） | Dr.COM 表单 | 上网密码 |
| 有线（统一认证） | CAS | 统一身份认证密码 |

实测这两个密码**不一样**（我们这边只差末尾一个 `@`）。

**影响**：只存一套密码时，另一套流程会一直报"账号或密码错误"，
而 CAS 那条还有"再输错 N 次锁定账号"的计数器 —— 很容易把用户账号撞锁。

**建议**：支持分开存两套密码（我们这边是两个钥匙串条目）。

## 5️⃣ 几个小坑（v1.1 已经修了的就不重复了）

- **登录路径必须带 `ver=1.0`**：不带会拿到后台管理页面而不是登录结果（v1.1 已修 ✅）
- **AJAX 头**：v1.1 说必须带 `X-Requested-With`。实测我们这台 AC **GET/POST、带不带头部都能通**，
  但带着更保险，建议保留。
- **`captcha_url` 要带 `/cas` 前缀**：`https://c.nua.edu.cn/cas/captchValid/checkCaptchImg`
  （v1.1 已修 ✅）
- **`--probe` 很有用**：建议保留，方便用户自查走哪套流程。

## 6️⃣ 夜间静默（`quiet_hours`）实测非常有效 ✅

v1.1 新增的夜间静默我们在一台真实机器上验证了一整夜：

```
23:53 在校园网且未认证
23:57 第 1 次失败 → 2 分钟后再试
23:59 第 2 次失败 → 5 分钟后再试
00:00 ⬛ 进入夜间静默 00:00-06:00（暂停所有网络请求）
06:00 ☀️ 夜间静默结束
06:15 ✅ 登录成功，网络已恢复
```

**0-6 点整整 6 小时，日志只有 1 行**，早上 6 点自动恢复并成功登录。
这个功能建议保留并保持默认开启。

## 7️⃣ macOS 适配的实现要点（供参考）

| 原版（Windows） | macOS 版 |
| --- | --- |
| DPAPI 加密存密码 | 钥匙串 Keychain（`security` 命令） |
| 计划任务 `schtasks` | launchd LaunchAgent（KeepAlive + RunAtLoad） |
| Playwright 驱动 Edge 拖滑块 | 不用浏览器，纯 HTTP |
| —— | 所有请求绑定物理网卡（`IP_BOUND_IF`），绕过 TUN 模式 VPN |
| —— | 自带迷你 DNS 客户端，绕过 Clash/Surge 的 fake-ip |
| —— | 有线/无线按客户端 IP 自动分流；支持两套密码 |

另外几个 macOS 特有的坑，也一并记录：

- **DNS 被 fake-ip 劫持**：系统解析 `c.nua.edu.cn` 返回 `198.18.x.x`（Clash 假地址），
  直接请求会打到黑洞。解决：绑定网卡 + 用校园 DNS（`112.4.0.55`）自解析真实 IP。
- **多网卡优先级**：macOS 默认让有线优先，插上网线瞬间默认路由切到未认证的有线，
  **在全网都会断**（我们实测断了 2 分钟，直到认证完成）。
  解决：把 Wi-Fi 调到服务顺序第 1 位（`networksetup -ordernetworkservices`）。
- **`fatal` 错误要早停**：把"密码错误 / 在线数超限 / 验证码"这类错误挑出来立即停手，
  否则换服务类型重试会连着打好几次，可能把账号撞锁。

## 8️⃣ 一点建议

- 指纹/人脸这类"需要真人"的验证，建议在文档里明确写"无法自动化"，
  免得用户以为是脚本坏了
- 建议把"有线也走 Dr.COM"做成**可选**而不是硬编码，因为不同学校/不同时期的策略可能不一样
- 建议保留 `--probe`，并在 README 里给一句"确认当前走哪套流程"的用法

## 9️⃣ 不同运营商走同一个门户，但账号后缀不同

学校两张校园 Wi-Fi 对应两家运营商，账号写法不同：

| 校园 Wi-Fi | 运营商 | 账号写法 |
| --- | --- | --- |
| `NUA-CMCC` | 移动 | 学号（不带后缀） |
| `NUA-@f-Young` | 电信 | 学号`@dx` |

（联通的同学用 学号`@lt`）

这个后缀来自门户页里写死的 `carrier` 配置：

```js
carrier='{"yys":{"title":"服务类型","mode":"radiobutton","type":"0","data":[
  {"id":"1","name":"校园用户","suffix":""},
  {"id":"2","name":"校园电信","suffix":"@dx"},
  {"id":"3","name":"校园联通","suffix":"@lt"},
  {"id":"4","name":"校园其他","suffix":""}],"defaultID":"1"}'
```

**实测**：移动账号用不带后缀可以登录；填 `@dx` / `@lt` 会被 AC 拒绝
（`Authentication fail` 或"账号错误(运营商登录请先绑定运营商账号)"）。

**给 Windows 版的建议**：

1. **`账号错误` / `Authentication fail` 不能当致命错误立即停手** ——
   它们正是"服务类型选错了"的表现，应该换下一个后缀继续试。
   真正的致命错误是：`密码` / `验证码` / `在线数超出限制`。
2. **试对之后建议记下来**，否则每次登录都要把 4 种组合全试一遍
   （macOS 版是按客户端网段分别记的：`state/carrier.json`，
   因为不同运营商可能是不同网段）。
3. 服务类型可以做成配置项（macOS 版是 `wifi_suffix`），
   想写死的同学直接填 `@dx` 就不用试了。

**另外：两家运营商的账号密码也不同。**

实测确认：移动和电信的账号、密码是两套。所以 macOS 版做成了
**按网段分别记录账号**（`config.json` 的 `accounts`，键是客户端 IP 前两段），
密码则按账号分别存钥匙串条目：

```json
"account": "B240000000",
"accounts": {"10.53": "B240000000", "10.54": "D12345678"}
```

用户操作体验：连上哪张网就运行一次 `--set-password`，各存一次即可。
建议 Windows 版也考虑同样的做法（现在只支持一套账号，换运营商的 Wi-Fi 就登不上）。

## 1️⃣1️⃣ 重要：学校的账号可用时段规则（对静默设计有影响）

实测确认，学校对不同账号的认证时段限制不同，**而且与连哪张校园网无关**：

| 账号类型 | 标识 | 可用时段 |
| --- | --- | --- |
| 学生账号 | 学号（`B` 开头） | **只有周六日 24 小时可用**；非周六日 `00:00-06:00` 无法认证 |
| 教师账号 | 工号（`M` 开头） | **所有时段都可用** |

**这个发现对 `quiet_hours` 的设计有影响：**

1. 原来的静默是"一刀切"——会导致教师账号在半夜掉线后也不去重连，
   而实际上那个时间段**恰恰是能认证的**。
2. 静默应该**按账号**判断，而不是按网段 —— 因为**同一张校园网（移动/电信）
   上同时存在学生账号和教师账号**，按网段判断必然出错。
3. macOS 版实现：`teacher_account_prefixes: ["M"]` —— M 开头的账号不受静默限制；
   `quiet_hours.days` 保持 `[0,1,2,3,4]`（周一~周五）就正好对应学生账号的规则，
   因为学生账号**周末是 24 小时可用的**，所以周末不该静默。

> 另外注意：判断静默时需要知道"当前网段用哪个账号"，而静默期间**不能发任何网络请求**
> —— 所以我们用 `route -n get` + `ifconfig` 读本地信息，不发包。
